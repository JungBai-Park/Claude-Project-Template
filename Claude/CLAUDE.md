# 폴더 구성

1. Documents : 
   이 폴더 밑에 적혀지는 문서들은 여러 세션에 걸쳐 AI가 프로젝트를 이어서 완성하기 위한 기록이다.
   **사용자가 읽는 문서가 아니며, 사용자에게 설명하려고 쓰지 않는다.** 따라서, mermaid-writer 스킬 호출도 하지 않는다.
	- DESIGN.md :
	  설계 내용을 기록하는 문서
	  세부 사항은 별도의 문서에 있으며, 이 문서는 별도의 문서에 대한 제목과 링크만 목차 형식으로 제공한다.
	- DESIGN\\ : 
	  설계 내용에 대한 각각의 세부 사항들이 보관되는 폴더
	- PITFALLS.md : 
	  프로젝트 진행 중 발생한 주요 실수, 시행착오, 그리고 해결 방법을 기록하는 문서
	  세부 사항은 별도의 문서에 있으며, 이 문서는 별도의 문서에 대한 제목과 링크만 목차 형식으로 제공한다.
	- PITFALLS\\ :
	  함정·트러블슈팅에 대한 각각의 세부 사항들이 보관된 폴더
	- PROGRESS.md : 
	  개발 진척 상황을 기록하는 문서
	  세부 사항은 별도의 문서에 있으며, 이 문서는 별도의 문서에 대한 제목과 링크만 목차 형식으로 제공한다.
	- PROGRESS\\ :
	  개발 진척 상황에 대한 각각의 세부 사항들이 보관되는 폴더
	- MEMORY\ :
	  autoMemoryDirectory 설정값으로 지정된 위치.
	  MEMORY는 클로드 코드가 스스로 내용을 관리하는 방식이므로, "마무리" 명령과 무관하게 작성된다.
	  (템플릿 사용 시: .claude\\settings.json의 autoMemoryDirectory를 이 프로젝트의 Documents\\MEMORY 절대 경로로 고친 뒤 이 줄을 지운다.)

2. Source\\ : 
   프로그램 제작에 필요한 파일들이 저장된 폴더
	- Code :
	  사용자와 AI가 만든 소스코드
	  배포용 실행파일을 만들기 위한 코드(또는 배포시 실행되는 코드)이므로, Test\\ 폴더의 코드를 호출하지 않아야 한다.
	- Data :
	  프로그램 실행 시 참조되는 데이터
	- Test :
	  테스트 목적으로 만들어 놓은 코드. (단, 보존가치가 있는 코드만 여기에 두며, 1회성으로 쓸 코드는 Temp\\에 만든다.)
	- Build :
	  개발환경(IDE)의 프로젝트 설정파일
	  실행파일 및 실행파일 제작을 위한 중간 산출물
	  사용자가 신경쓰지 않아도 되는 소스코드 (IDE 자동생성코드, 제3자 제공코드, 오픈소스)

3. Temp\\ :
   임시 파일은 시스템 스크래치패드에 만들지 않고 이 Temp\\ 폴더에 만든다.
   세션 종료 후 깨끗이 지워져도 상관없는 파일만 둔다.
   Temp에 어떤 파일을 생성/삭제/변경 했다고 보고할 필요는 없다.

4. Reference\\ :
   참고용 파일
   사용자가 관리하는 폴더이며, 불필요한 파일은 수시로 삭제 될 수 있다.
	  
# 세션 시작 시 문서 읽는 순서

1. `PROGRESS.md`의 "현재 진행 중인 업무"를 확인하고, 해당 세부 문서의 "현재 상태 및 다음 단계"부터 읽는다.
   진행 중인 업무가 여럿이면 사용자가 지정한 업무의 세부 문서만 읽는다.
2. 그 밖의 문서(DESIGN, PITFALLS, 개발환경 등)는 작업에 필요할 때만 읽는다.
3. "완료된 업무"의 세부 문서는 그 업무를 다시 다룰 때만 읽는다.

# 파일 및 디렉토리의 생성 규칙

1. 승인 없이 파일 및 디렉토리를 생성 가능한 폴더 :
   AI가 파일 및 디렉토리를 생성할 때는, 그 목적에 따라 Documents의 하위 디렉토리(DESIGN\\, PROGRESS\\, PITFALLS\\, MEMORY\\),
   Source의 하위 디렉토리(Code\\, Data\\, Test\\, Build\\) 그리고 Temp\\에 배치 할 수 있다.
2. 그 외의 폴더 (예: 프로젝트 루트, Source\\ 바로 밑, Documents\\ 바로 밑, Reference\\ 내부)는 사용자의 승인을 받아야 한다.

# 문서의 작성 및 갱신 규칙

1. 토큰 절약을 위해 불필요한 내용(더이상 유효하지 않은 설계 내용, 취소된 계획 등)을 적어 두지 않는다.
2. 특히, 다음과 같이 적지 않도록 주의한다.
	- BAD(이 값은 2026년 11월 07일, 3에서 4로 바뀌었다.) -> GOOD(이 값은 4이다.)
	- BAD(전에는 이렇게 하기로 했으나 2026년 11월 07일 더이상 하지 않기로 했다.) -> GOOD = 삭제
3. 문서 작성 및 갱신은 "마무리" 때 일괄로 한다.
	- 다음과 같은 상황에서도 문서에 즉시 반영하지 않고, 세션 종료를 위한 "마무리" 요청 때 문서에 반영한다.
		- 사용자와의 대화를 통해 설계 내용이 결정 되었을 때
		- 작업 중 함정(PITFALL)을 만나 우회방법으로 처리 했을 때
		- 작업 후, PROGRESS.md의 완료·미완료 표시
		- 파일을 옮기거나 이름을 바꿔 문서에 적힌 경로가 어긋나는 것이 발견된 경우
	- 예외는 사용자가 특정 사항을 문서에 반영하라고 명시적으로 요청한 경우뿐이다. 이때도 요청한 사항만 반영한다.
4. 세부 문서(DESIGN\\, PITFALLS\\, PROGRESS\\ 아래)의 파일 이름은 번호_주제.md로 한다.
	- 번호는 폴더마다 001부터 세 자리로 매기며, 001은 양식이다.
	- 새 문서는 그 폴더에서 가장 큰 번호의 다음 번호를 쓴다.
	- 주제에 공백을 넣으려면 `_`로 바꾼다.
	- 삭제된 문서의 번호는 결번으로 두고 다시 쓰지 않는다.

# Issue 상황 대화 방법

1. Issue 상황이란, 개발과정에서 사용자와의 협의를 필요로 하는 내용이 발생한 상황을 말한다.
2. AI는 사용자가 올바른 판단을 할 수 있도록 다음과 같은 정보를 제시하며 질문을 한다.
	- 발생 조건 : 어떤 경우(입력, 사용 상황, 문서 형태)에 그 issue가 발생하는가?
	- 문제점 : 발생하면 무엇이 왜 문제인가? (잘못된 결과, 오류, 판단하지 못하는 지점 등)
	- 용어 설명 : 질문에 사용된 용어에 대해 설명 (사용자가 알고 있다고 생각되는 경우는 생략)
3. Issue 사항을 다음에 검토할 수 있도록 문서에 반영할 때,
   현재 세션의 문맥(context)을 모르는 다음 세션이 해당 issue를 사용자와 대화하기 위해 필요한 모든 정보를 적어 둔다.
